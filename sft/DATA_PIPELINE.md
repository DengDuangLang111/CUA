# 从轨迹到训练数据:流水线怎么 work,每道闸在挡什么

> 这条流水线把**教师跑出来的原始轨迹**变成**能喂给 ms-swift 的训练样本**。
> 命令在 `CUA/RUNBOOK.md`(唯一 runbook),设计与教训在这里。
> 一句话:**每一层只做一个判断,每道闸只挡一类错,没有任何一层被信任到不用复核。**

---

## 0 全景

```
 ① rollout            教师在 VM 里跑任务,逐步落盘
    results_generated/<model>/<run>/<domain>/<task_id>/
        traj.jsonl · obs_*.png · initial_state.png · result.txt
                    │
 ② traj.load_steps   一行一动作 → 一步一样本(多动作步合并)
                    │
 ③ trajaudit         判官给整条轨迹打分(问卷 v1 / v2 / v2req)
                    │
 ④ arb               checker 与判官分歧时仲裁(v1 / v2 两段式 / adv 对抗辩护)
                    │
 ⑤ curate            出名单:keep / rescue / drop / tier1 / tier2
                    │     ← 原则:判官提名,仲裁定罪;只有证据能封杀
 ⑥ terminalfix       修结尾:三条路径,最小干预
                    │
 ⑦ build             渲染上下文 + 目标 → samples.jsonl + images/
                    │
 ⑧ verify            出包硬门(内部自洽)
                    │
 ⑨ corpusaudit       出包审计(对照原始轨迹)  ← verify 做不到的那一半
                    │
 ⑩ to_swift + ship   转 ms-swift 格式,推到 Tillicum,行数与图数核对
                    │
 ⑪ sbatch preflight  作业启动时再验一次:每个绝对图片路径在集群上存在
```

---

## 1 每一层负责什么

| 层 | 输入 | 输出 | 它唯一负责的判断 |
|---|---|---|---|
| `traj.py` | `traj.jsonl` | `[Step(num, response, actions, screenshot)]` | 一步的边界在哪、哪一帧是它的观察 |
| `trajaudit.py` | 轨迹 + 任务 | 每条一个分数 + 理由 | 这条轨迹**做成了没有** |
| `arb.py` | checker 判定 + 判官判定 | 裁决 + 理由 | 两者冲突时**谁错了** |
| `curate.py` | 判官 + 仲裁 + 步级审计 | 五张名单 | 这条**进不进语料** |
| `terminalfix.py` | 轨迹 + 名单 | 每条一行「结尾怎么修」 | 这条**怎么收尾** |
| `build.py` | 轨迹 + 名单 + 结尾修复 | `samples.jsonl` + `images/` | 模型**看到什么、学什么** |
| `verify.py` | 语料 | exit 0/1 | 语料**内部自洽吗** |
| `corpusaudit.py` | 语料 + 原始轨迹 | 8 项检查 + JSON | 语料**还忠于原始轨迹吗** |

**关键分工**:`verify` 只看语料自己;`corpusaudit` 要回头读原始轨迹。
后者慢得多(每臂 3–5 分钟,开 `--verify-pixels` 要几十分钟),所以不进 build 快路径,
定位在 **build 之后、ship 之前跑一次**。

## 2 五道闸,以及每道**挡不住**什么

这张表是整份文档的重点。**每道闸都有它照不到的地方,所以才需要下一道。**

| 闸 | 在哪 | 能挡 | **挡不住** |
|---|---|---|---|
| slug 唯一 | `taskgen/merge.py` | 两个任务共用一个 slug | 已经生成好的旧数据 |
| 图片 key 唯一 | `build.py` | 两个任务写进同一个图片目录 | 目录名对、**里面的像素是错的** |
| 存在性 | `verify.py` | 图片缺失 / 空文件 | 图片存在但**内容不对** |
| 目录归属 | `verify.py` | 一个图片目录被两个 task_id 引用 | 污染**从上一代语料继承**过来(目录名唯一,归属唯一,像素仍是错的) |
| **图片 key 带 task_id** | `build.py` | **全部**——两条轨迹在结构上无法写进同一目录 | (无) |

### 同一招用在截尾上:画面硬门,以及它为什么偏保守

`terminalfix.decide_keep_to` 用同一个思路守截尾:启发式提出切点后,
**强制比对「终止帧」与「原末步帧」的 md5**,不一致就整条退回 last-only。

这道门**故意偏保守**:它用的是原始 md5,而 GNOME 顶栏的**时钟字形**
(8×10 px,坐标 (1031,8)-(1039,18))每分钟都在变。独立审计逐像素复核 33 条截尾后
给出真实分布:

| | 条数 |
|---|---|
| 字节完全相同 | 8 |
| 只差一个时钟字形 → 语义相同 | 13 |
| 只差光标闪烁/tooltip(≤225 px) | 4 |
| **真正不同**(最大一条差了 23.9% 屏幕) | **8** |

也就是说硬门退回了 25 条,而**必须退的只有 8 条**。多退的 17 条代价是语料里多留
一两个 WAIT 步 —— 而收益是**判据里不需要写死"屏蔽屏幕某个矩形"这种手工规则**。
用可证明的严格判据换掉一点点数据,这笔交易划算。

**另外**:画面相同也**不等于**磁盘状态相同。审计找到 2 条轨迹被砍掉的是一次
**非冗余的 ctrl+S**(画面只差 40 px,文件内容却不同)。所以画面硬门是必要条件、
不是充分条件 —— 这也是它宁可保守的另一个理由。

**像素重推导检查已删除**(2026-08-17):它每臂要花 45 分钟重编码 6.2 万张 PNG,
而它防的那件事已经被根因修复消除 —— `img_key` 永远带 `task_id`,两条轨迹
不可能写进同一目录,`verify` 的"0 个目录被两个 task_id 引用"就是这件事的确认。
**唯一性是结构保证,再逐像素确认一遍是用最贵的方式学到零信息。**

## 3 三次真实事故,和它们各自被哪道闸接住

| 事故 | 机制 | 现在被谁接住 |
|---|---|---|
| **slug 冲突** (08-15 发现) | v11-500 合并时 3 组任务撞 slug,slug 命名的图片目录被后者覆盖,前者的样本指向别人的像素 | merge 拒绝冲突 + build 的 key 唯一 |
| **修复本身成了传播管道** (08-17) | 第一版修复**只给冲突对里的第二个任务加后缀**,第一个仍用裸 slug;而 `--image-cache` 从旧目录按裸 slug 取图,取到的正是第二个任务的像素 | build 的 key **永远**带 task_id(旧缓存必然 miss)+ `--verify-pixels` |
| **auto 截尾砍掉真动作** (08-17) | `stalled_tail` 用 `any(动作 == WAIT)` 判"这步没干活",而 agent 的习惯是「点一下 + 等一下」,于是生产性步被判死,倒着走的循环吃掉整条轨迹 | 判据改 `all(is_noop)` + **画面硬门**(终止帧必须与原末步帧字节相同,否则整条退回) |

**共同教训**:`存在性检查 ≠ 正确性检查 ≠ 归属检查`。
而且——**修复本身也需要被审计**。第二次事故就是第一次的修复造成的。

## 4 `terminalfix` 的三条路径(最小干预)

结尾是这条流水线里唯一"我们主动改写模型输出"的地方,所以按最小干预分流:

| 原始结尾 | 处理 | 实测条数 |
|---|---|---|
| 已经是 `terminate(success)` 且未截尾 | **完全不动**(行里 `response: null`,build 跳过) | 48 |
| 完整的散文结尾 | **保留教师原话,只补上缺的 tool call** | 259 |
| `call_user` / 截尾 / 末步是真动作 / 踩 infeasible 触发词 | 教师重写(`thinking` + 可见 `statement`) | 69 |
| 重写两次仍踩触发词 | **整条不出包**(`mode: exclude`) | 0 |

**出口闸(2026-08-17 加)**:`looks_infeasible_response` 是把轨迹**路由进**重写路径的
谓词之一,但重写产出**从来没有再被它查过** —— 结果复发了:`os/e35e4ef1` 的任务就是
清空文件夹,成功的屏幕证据字面写着 `Folder is Empty`,而这个短语在 harness 那张
57 条子串表里。它眼下不炸(该谓词只在"没有任何工具调用"时被查,而我们的结尾有
terminate),但它进了训练目标。

现在重写产出会**用当初路由它的那个谓词再查一遍**:命中就带约束重试(明确要求换个
说法描述同一份证据,别照抄 UI 标签),再命中就把整条标 `exclude` 不出包。
实测:命中数 1 → **0**,且靠重试就绕开了(改说 `contains no files`),**没有轨迹被排除**。

**教训**:**能用来做路由判断的谓词,就该用来做出口校验。** 这条是人工复查发现的,
不是任何闸抓出来的。

### 语料自带来路标记(2026-08-17 加)

每个样本的 meta 现在带 `terminal_mode`(`untouched` / `already-terminate` /
`append` / `rewrite`)和 `rescued`(checker 是否判败后被赎回)。

**为什么必须写进语料**:末步现在有**三种来路**,而它们在语料里长得一模一样。
以前要回答"append 和 rewrite 哪个更有害""赎回轨迹表现如何",只能回头 join
`terminal_*.jsonl` 和 curate 名单——**而这两样都不随语料发布**。训练完再想归因就晚了。

**为什么不一刀切重写**:第一版把全部 376 条都换成合成结尾,其中 **54 条本来就是
正确的 terminate** —— 那是倒退。现在 **307 条保留 Qwen3.8 自己的原话**,教师调用
从 362 次降到 69 次。

**为什么重写要带可见 statement**:教师自然产生的 68 条 terminate 结尾**100%** 在
`</think>` 与 `<tool_call>` 之间有一句给人看的话,语料里其他目标也有 75.3% 有。
第一版一句都不写,让末步成了全语料唯一的形状 —— 而这个臂要修的病,恰恰是
**学生照抄教师的终止风格**。

## 5 反复踩的坑(排错先看这里)

| 症状 | 真因 |
|---|---|
| 改了代码但行为没变 | **`__pycache__` 里的旧字节码**。跑之前 `rm -rf __pycache__` + `PYTHONDONTWRITEBYTECODE=1` |
| 教师返回的理由全是同一句 | 漏传 `--model`(`anthropic_cfg` 原样透传模型名),调用失败被静默吞掉 → 兜底句。现在错误会 surface,空理由自动判为 stale 重跑 |
| 本地 serve 不按 JSON 回 | **这个 serve 静默忽略 `guided_json`**(`trajaudit.qwen_contract` 早有记录)。要在 system prompt 里下"只回一个 JSON 对象"的契约 |
| vLLM 回来的样本全被记成"散文结尾" | thinking 模式下 `content` 为 `null`,文本在 `reasoning_content`。两个字段都要读 |
| `--tasks` 传了 `examples/` 就崩 | `load_instruction` 自己拼 `examples/`,要传 **run 目录** |
| 审计报"所有图片都缺失" | 图片路径**相对各自 build 目录**(ship 时才转绝对),别按进程 cwd 解析 |
| 审计报出大量不存在的目录冲突 | 目录归属键必须用**绝对路径**;两个 pool 各自 build 目录下同名相对路径是合法的 |
| **训练实际样本数比语料少,且无从追认** | `truncation_strategy` 默认 **`delete`**,而 delete 是**完全静默**的:args 层翻译成 raise → `template/base.py:1497` 抛 `MaxLengthError` → `dataset/preprocessor/core.py:200-206` `pass` + `row = []`。日志零记录,`[INFO:swift] train_dataset num_rows` 打印的是**丢弃前**的数(实测 247800 报 6474、240274 报 6385,都等于原始行数)。**row counts lie** —— 只能用 `ostg.sft.vlcheck maxlen` 事前数 |
| 按 task_id 找轨迹得出离谱结论 | 同一 task_id 在**多个 model/run** 下都有且轨迹完全不同。必须按 `meta['run']` 定位 + `orig_steps` 校验 |

## 6 诊断工具(不在主链路上)

| 模块 | 回答什么问题 |
|---|---|
| `termprobe.py` | 固定模型/任务/模板,只动温度,结束方式怎么变。**实测:温度解释不了终止缺口**(0.6 下 3%,1.0 下 10%,对照 Qwen3.6 的 96%) |
| `stepaudit.py` | 步级审计:哪些步是弱证据、哪些是幻觉动作 |

## 7 跑法

命令一律见 `CUA/RUNBOOK.md` §筛选四步全流水 与 §终止规范化。
**提交规矩**:数据生成代码先入 git 再跑,日志记 code hash;
推文件到 WSL 后**必对 md5**,不一致就当没推。
