# 从轨迹到训练数据:流水线怎么 work,每道闸在挡什么

> 这条流水线把**教师跑出来的原始轨迹**变成**能喂给 ms-swift 的训练样本**。
> 命令在 `CUA/RUNBOOK.md`(唯一 runbook),设计与教训在这里。
> 一句话:**每一层只做一个判断,每道闸只挡一类错,没有任何一层被信任到不用复核。**

---

## 0 全景

```
 ① rollout            教师在 VM 里跑任务,逐步落盘
    results_generated/<model>/<run>/<domain>/<task_id>/
        traj.jsonl · obs_*.png · initial_state.png · result.txt
                    │
 ② traj.load_steps   一行一动作 → 一步一样本(多动作步合并)
                    │
 ③ trajaudit         判官给整条轨迹打分(问卷 v1 / v2 / v2req)
                    │
 ④ arb               checker 与判官分歧时仲裁(v1 / v2 两段式 / adv 对抗辩护)
                    │
 ⑤ curate            出名单:keep / rescue / drop / tier1 / tier2
                    │     ← 原则:判官提名,仲裁定罪;只有证据能封杀
 ⑥ terminalfix       修结尾:三条路径,最小干预
                    │
 ⑦ build             渲染上下文 + 目标 → samples.jsonl + images/
                    │
 ⑧ verify            出包硬门(内部自洽)
                    │
 ⑨ corpusaudit       出包审计(对照原始轨迹)  ← verify 做不到的那一半
                    │
 ⑩ to_swift + ship   转 ms-swift 格式,推到 Tillicum,行数与图数核对
                    │
 ⑪ sbatch preflight  作业启动时再验一次:每个绝对图片路径在集群上存在
```

## 1 每一层负责什么

| 层 | 输入 | 输出 | 它唯一负责的判断 |
|---|---|---|---|
| `traj.py` | `traj.jsonl` | `[Step(num, response, actions, screenshot)]` | 一步的边界在哪、哪一帧是它的观察 |
| `trajaudit.py` | 轨迹 + 任务 | 每条一个分数 + 理由 | 这条轨迹**做成了没有** |
| `arb.py` | checker 判定 + 判官判定 | 裁决 + 理由 | 两者冲突时**谁错了** |
| `curate.py` | 判官 + 仲裁 + 步级审计 | 五张名单 | 这条**进不进语料** |
| `terminalfix.py` | 轨迹 + 名单 | 每条一行「结尾怎么修」 | 这条**怎么收尾** |
| `build.py` | 轨迹 + 名单 + 结尾修复 | `samples.jsonl` + `images/` | 模型**看到什么、学什么** |
| `verify.py` | 语料 | exit 0/1 | 语料**内部自洽吗** |
| `corpusaudit.py` | 语料 + 原始轨迹 | 8 项检查 + JSON | 语料**还忠于原始轨迹吗** |

**关键分工**:`verify` 只看语料自己;`corpusaudit` 要回头读原始轨迹。
后者慢得多(每臂 3–5 分钟,开 `--verify-pixels` 要几十分钟),所以不进 build 快路径,
定位在 **build 之后、ship 之前跑一次**。

## 2 五道闸,以及每道**挡不住**什么

这张表是整份文档的重点。**每道闸都有它照不到的地方,所以才需要下一道。**

| 闸 | 在哪 | 能挡 | **挡不住** |
|---|---|---|---|
| slug 唯一 | `taskgen/merge.py` | 两个任务共用一个 slug | 已经生成好的旧数据 |
| 图片 key 唯一 | `build.py` | 两个任务写进同一个图片目录 | 目录名对、**里面的像素是错的** |
| 存在性 | `verify.py` | 图片缺失 / 空文件 | 图片存在但**内容不对** |
| 目录归属 | `verify.py` | 一个图片目录被两个 task_id 引用 | 污染**从上一代语料继承**过来(目录名唯一,归属唯一,像素仍是错的) |
| **图片 key 带 task_id** | `build.py` | **全部**——两条轨迹在结构上无法写进同一目录 | (无) |

### 同一招用在截尾上:画面硬门,以及它为什么偏保守

`terminalfix.decide_keep_to` 用同一个思路守截尾:启发式提出切点后,
**强制比对「终止帧」与「原末步帧」的 md5**,不一致就整条退回 last-only。

这道门**故意偏保守**:它用的是原始 md5,而 GNOME 顶栏的**时钟字形**
(8×10 px,坐标 (1031,8)-(1039,18))每分钟都在变。独立审计逐像素复核 33 条截尾后
给出真实分布:

| | 条数 |
|---|---|
| 字节完全相同 | 8 |
| 只差一个时钟字形 → 语义相同 | 13 |
| 只差光标闪烁/tooltip(≤225 px) | 4 |
| **真正不同**(最大一条差了 23.9% 屏幕) | **8** |

也就是说硬门退回了 25 条,而**必须退的只有 8 条**。多退的 17 条代价是语料里多留
一两个 WAIT 步 —— 而收益是**判据里不需要写死"屏蔽屏幕某个矩形"这种手工规则**。
用可证明的严格判据换掉一点点数据,这笔交易划算。

**另外**:画面相同也**不等于**磁盘状态相同。审计找到 2 条轨迹被砍掉的是一次
**非冗余的 ctrl+S**(画面只差 40 px,文件内容却不同)。所以画面硬门是必要条件、
不是充分条件 —— 这也是它宁可保守的另一个理由。

**像素重推导检查已删除**(2026-08-17):它每臂要花 45 分钟重编码 6.2 万张 PNG,
而它防的那件事已经被根因修复消除 —— `img_key` 永远带 `task_id`,两条轨迹
不可能写进同一目录,`verify` 的"0 个目录被两个 task_id 引用"就是这件事的确认。
**唯一性是结构保证,再逐像素确认一遍是用最贵的方式学到零信息。**

## 3 三次真实事故,和它们各自被哪道闸接住

| 事故 | 机制 | 现在被谁接住 |
|---|---|---|
| **slug 冲突** (08-15 发现) | v11-500 合并时 3 组任务撞 slug,slug 命名的图片目录被后者覆盖,前者的样本指向别人的像素 | merge 拒绝冲突 + build 的 key 唯一 |
| **修复本身成了传播管道** (08-17) | 第一版修复**只给冲突对里的第二个任务加后缀**,第一个仍用裸 slug;而 `--image-cache` 从旧目录按裸 slug 取图,取到的正是第二个任务的像素 | build 的 key **永远**带 task_id(旧缓存必然 miss)+ `--verify-pixels` |
| **auto 截尾砍掉真动作** (08-17) | `stalled_tail` 用 `any(动作 == WAIT)` 判"这步没干活",而 agent 的习惯是「点一下 + 等一下」,于是生产性步被判死,倒着走的循环吃掉整条轨迹 | 判据改 `all(is_noop)` + **画面硬门**(终止帧必须与原末步帧字节相同,否则整条退回) |

**共同教训**:`存在性检查 ≠ 正确性检查 ≠ 归属检查`。
而且——**修复本身也需要被审计**。第二次事故就是第一次的修复造成的。

## 4 `terminalfix` 的三条路径(最小干预)

结尾是这条流水线里唯一"我们主动改写模型输出"的地方,所以按最小干预分流:

| 原始结尾 | 处理 | 实测条数 |
|---|---|---|
| 已经是 `terminate(success)` 且未截尾 | **完全不动**(行里 `response: null`,build 跳过) | 48 |
| 完整的散文结尾 | **保留教师原话,只补上缺的 tool call** | 259 |
| `call_user` / 截尾 / 末步是真动作 / 踩 infeasible 触发词 | 教师重写(`thinking` + 可见 `statement`) | 69 |
| 重写两次仍踩触发词 | **整条不出包**(`mode: exclude`) | 0 |

**出口闸(2026-08-17 加)**:`looks_infeasible_response` 是把轨迹**路由进**重写路径的
谓词之一,但重写产出**从来没有再被它查过** —— 结果复发了:`os/e35e4ef1` 的任务就是
清空文件夹,成功的屏幕证据字面写着 `Folder is Empty`,而这个短语在 harness 那张
57 条子串表里。它眼下不炸(该谓词只在"没有任何工具调用"时被查,而我们的结尾有
terminate),但它进了训练目标。

现在重写产出会**用当初路由它的那个谓词再查一遍**:命中就带约束重试(明确要求换个
说法描述同一份证据,别照抄 UI 标签),再命中就把整条标 `exclude` 不出包。
实测:命中数 1 → **0**,且靠重试就绕开了(改说 `contains no files`),**没有轨迹被排除**。

**教训**:**能用来做路由判断的谓词,就该用来做出口校验。** 这条是人工复查发现的,
不是任何闸抓出来的。

### 语料自带来路标记(2026-08-17 加)

每个样本的 meta 现在带 `terminal_mode`(`untouched` / `already-terminate` /
`append` / `rewrite`)和 `rescued`(checker 是否判败后被赎回)。

**为什么必须写进语料**:末步现在有**三种来路**,而它们在语料里长得一模一样。
以前要回答"append 和 rewrite 哪个更有害""赎回轨迹表现如何",只能回头 join
`terminal_*.jsonl` 和 curate 名单——**而这两样都不随语料发布**。训练完再想归因就晚了。

**为什么不一刀切重写**:第一版把全部 376 条都换成合成结尾,其中 **54 条本来就是
正确的 terminate** —— 那是倒退。现在 **307 条保留 Qwen3.8 自己的原话**,教师调用
从 362 次降到 69 次。

**为什么重写要带可见 statement**:教师自然产生的 68 条 terminate 结尾**100%** 在
`</think>` 与 `<tool_call>` 之间有一句给人看的话,语料里其他目标也有 75.3% 有。
第一版一句都不写,让末步成了全语料唯一的形状 —— 而这个臂要修的病,恰恰是
**学生照抄教师的终止风格**。

## 5 反复踩的坑(排错先看这里)

| 症状 | 真因 |
|---|---|
| 改了代码但行为没变 | **`__pycache__` 里的旧字节码**。跑之前 `rm -rf __pycache__` + `PYTHONDONTWRITEBYTECODE=1` |
| 教师返回的理由全是同一句 | 漏传 `--model`(`anthropic_cfg` 原样透传模型名),调用失败被静默吞掉 → 兜底句。现在错误会 surface,空理由自动判为 stale 重跑 |
| 本地 serve 不按 JSON 回 | **这个 serve 静默忽略 `guided_json`**(`trajaudit.qwen_contract` 早有记录)。要在 system prompt 里下"只回一个 JSON 对象"的契约 |
| vLLM 回来的样本全被记成"散文结尾" | thinking 模式下 `content` 为 `null`,文本在 `reasoning_content`。两个字段都要读 |
| `--tasks` 传了 `examples/` 就崩 | `load_instruction` 自己拼 `examples/`,要传 **run 目录** |
| 审计报"所有图片都缺失" | 图片路径**相对各自 build 目录**(ship 时才转绝对),别按进程 cwd 解析 |
| 审计报出大量不存在的目录冲突 | 目录归属键必须用**绝对路径**;两个 pool 各自 build 目录下同名相对路径是合法的 |
| **训练实际样本数比语料少,且无从追认** | `truncation_strategy` 默认 **`delete`**,而 delete 是**完全静默**的:args 层翻译成 raise → `template/base.py:1497` 抛 `MaxLengthError` → `dataset/preprocessor/core.py:200-206` `pass` + `row = []`。日志零记录,`[INFO:swift] train_dataset num_rows` 打印的是**丢弃前**的数(实测 247800 报 6474、240274 报 6385,都等于原始行数)。**row counts lie** —— 只能用 `ostg.sft.vlcheck maxlen` 事前数 |
| 按 task_id 找轨迹得出离谱结论 | 同一 task_id 在**多个 model/run** 下都有且轨迹完全不同。必须按 `meta['run']` 定位 + `orig_steps` 校验 |

### 扫 swift 多轮语料的两个必踩坑(2026-08-19,两个会话同时栽进去)

swift 的**一行 = 截到第 k 步的整段多轮对话**,不是单轮。20 图的样本里有 30 个
assistant 段。由此:

1. **目标是最后一个 assistant 轮,不是第一个。** 用 `next(...)` 取第一个会永远
   拿到第 1 步的开场白 —— 症状是"所有样本的 target 长度一模一样"
   (38 个样本全是 5207 字符),看着像语料坏了,其实是扫描器坏了。
2. **动作在 `arguments.action`,不在 `name`。** Hermes JSON 的形状是
   `{"name":"computer_use","arguments":{"action":"terminate","status":"success"}}`,
   抓 `name` 会把每个终止步都报成 `computer_use`。
3. **别用 `"terminate"` 子串匹配**:think 文字里提到该词会误报(抽查 17 个 task 中招)。

**正确判据**:读每行最后一个 assistant 轮 → 取最后一个 `<tool_call>` 块 →
解析 `arguments.action`。

这两个坑叠加,曾让我们一度以为 4 条轨迹没有收尾监督、`corpusaudit` 报的
"0 endings not terminate" 是假的。修正后:**362/362 任务都有唯一终止行**,
语料与 corpusaudit 双双无罪。但这次误诊意外揪出了真问题 —— 其中 **3 条的终止行
带 18 张图、超过 65536**,`truncation_strategy=delete` 会精确删掉这三条轨迹的
收尾示范(决策与实测见 `sft/TRAINING.md` 现状块的 max_length 条目)。

## 8 工具故障会伪装成对象故障(2026-08-19,一天撞四次)

**判据:凡是"结论只有一个数、中间量一个不打"的工具,出错时必然嫁祸给被测对象。**

当天的四个实例,四次里有三次的第一反应都是怀疑训练或集群:

| 工具错在哪 | 看起来像什么 | 真相 |
|---|---|---|
| `tqdm` 在续训作业上拿总步数当分母 | "8节点×1卡比2节点×8卡快 2.3 倍" | 249176 从 ckpt-110 续训只跑 40 步,tqdm 除的是 150;真值 323 s/it 而非 88 |
| 进度条被 `lr_scheduler.step()` 警告冲掉 | "训练卡在 0/306" | 实际已到第 6 步,八卡 GPU 全 100%,loss 1.209→1.159 在降 |
| 三层 ssh 嵌套吃掉 grep 模式 | "5 分钟内 loss 行没涨,训练停了" | `grep -c ^.{.loss.:` 的引号被逐层剥掉,静默匹配不到任何东西返回 0 |
| builder 透传相对路径 | "图片全丢了" | 源语料存 `images/<task>/obs_NNN.png`,只在自己的构建目录里 resolve;作业 249537 四秒暴毙 |

**解法是让工具打印自己的关键中间量,而不是只报最终结论:**

- **步时**:打印步号区间、是否 `resume_from_checkpoint`,不要只给 `s/it`。
  引用任何 s/it 之前先确认该作业不是续训。
- **计数**:打印匹配到的模式和样本行,不要只给数字。一个返回 0 的计数器,
  和一个"确实是 0"的世界,长得一模一样。
- **路径改写**:打印改写条数 + 一条样本路径,**且条数要能和下游的报错数对上**。
  `strip_prose` 现在打 `13436 refs, 13436 rewritten to absolute` ——
  13,436 正是 preflight 报的失败数,一眼可对。
- **缺参数**:在构建期就预告下游会怎么死。`--images-prefix` 缺失时直接警告
  "这份语料 ship 出去会 preflight 失败",把爆点从作业启动提前到构建日志。

同类的既有条目:`log the choice, not just the result`(选权重的代码必须打印
它选了什么,见 `OPS.md`)。那条讲的是选择,这条讲的是测量与构建 —— 同一个病。

### 第五种:方法对了、输入形状错了(2026-08-19 同日,我栽的)

前四种是工具坏了,这一种更隐蔽:**工具没坏,是喂给它的输入不是生产环境的形状**。

当天我用 `tokenizer.apply_chat_template` 测"eval 时历史 `<think>` 还在不在",
结论"被剪光",还据此跟用户讲了一通"prose 是 eval 唯一的自然语言记忆载体"。
两路独立实测(另一会话的活体 `/v1/chat/completions/render` + 我的离线复验)
都推翻了它:**历史 think 全部保留**。

错在我手搓的 messages 里 user 轮是普通文本,而这个 harness 的每个非首轮 user
都包在 `<tool_response>` 里。模板的倒序扫描只在"不带该包装的 user 轮"处停下:
```jinja
{%- if not(content.startswith('<tool_response>') and content.endswith('</tool_response>')) %}
    {%- set ns.last_query_index = index %}
```
普通 user 轮 → 扫描停在最后一个 user → 历史轮全部走剥除分支;
真实形状 → 26/27 个 user 轮被跳过 → `last_query_index` 钉在 1 → 历史轮全部保留。
**generic chat 会剥,这个 harness 的形状不会。**

实测对照(真实 payload 54 条消息 / 26 个带 think 的 assistant 轮):
```
                真实形状(user带tool_response)   手搓形状(普通user)
Qwen3.5-4B           27 个 <think>                    1 个
Qwen3-VL-4B          27 个 <think>                    1 个
```

**规矩**:任何涉及 chat template 行为的实验(think 去留、tool_call 渲染、
system 拼接),**输入必须取自 `draft/message_cache/qwen_messages_step_*.json`
的真实 payload,不许手搓 messages**;并且必须带一个"能让被测行为翻面"的
灵敏度对照(这里是剥掉 `<tool_response>` 包装),否则无法区分"结论成立"
和"方法对任何输入都给同一个答案"。

更深一层的教训:**这条早就写在 `sft/RESULTS.md` §5.7 里**
("On generic chat messages the template does strip; on the message shape this
harness actually produces it does not"),我没查就自己重推了一遍。
先查 md 是防线,跳过防线的代价是一整条错误推论已经讲给了用户。

## 9 静默失效:不报错,数字只是悄悄变小(2026-08-22 归纳,九例)

§8 讲的是"工具坏了却看起来像对象坏了"。这一节讲一个更窄、更毒的子类:
**故障不产生任何错误信号 —— 没有异常、没有告警、没有日志 —— 只是让某个
数字比它应该的小。** 这类故障能存活数天到数周,因为一切"看起来在跑"。

九个案例,全部真实发生过:

| # | 故障 | 表面现象 | 实际损失 |
|---|---|---|---|
| 1 | `truncation_strategy=delete` 丢超长样本 | 训练正常启动 | max_length 65536 丢 14 条,40960 丢 1,116 条(17%)。**原型案例**,详见 §5 |
| 2 | 上游 `reasoning_content`→`reasoning` 改名 | 回复开头多两个空行 | 推理被生成、被计费、被丢弃;历史 think 变空又被模板整块丢掉,**上下文静默瘦 ~88%**;official-361 跑出 7,906 步 0 个 `<think>` |
| 3 | `fold_size>1` 的锯齿 | 参数写着 `image_max=20` | 稳态可见图在 11–20 之间跳,**均值只有 15.7**;`image_max=3` 配默认 `fold_size=10` 曾让 64.6% 样本全盲 |
| 4 | serve 断档但 runner 不死 | eval 继续推进、进度条正常 | 请求失败被当成任务失败,**157 题静默灌 0**;若未发现,nocap 的 361 会是 25.75% 而不是 47.00%,得出"SFT 有害"的反向结论 |
| 5 | 读取失败静默回退默认值 | 闸和监控都"正常判定" | `MODEL_BOUNDARY` 键名写错(`tasks_file` vs `tasks`),异常被吞、回退魔数 50,**261 题的臂被判成 50 题就完成** |
| 6 | 验证视图被截断 | `diff` 输出"看起来"没有该 hunk | `head -12` 恰好截掉 sed 生效的那段,于是得出"改动没生效"的结论,两侧各自"正常"地指向不同端口 |
| 7 | `ship_dataset.sh` 硬编码只 tar train | ship 打印 `SHIP OK`,计数全对 | 语料带 `--val-ratio` 建出来,`val_swift.jsonl` **根本没过去**;校验只数 train 的行,自然对得上 |
| 8 | `save_steps` 按旧语料条数算 | 训练正常,checkpoint 正常落盘 | 验证集切走 261 条后 97 步/epoch(不是 102),a5v 的 checkpoint 落在 epoch 1.05/2.10/3.15,**epoch-3 模型不存在且事后造不出来** |
| 9 | 复制模板建新配置,残留指向源模板 | 作业正常启动,日志正常,分数正常产出 | 7 个 serve 脚本的 `$SELF`(撞墙自续期的目标)指向别人的脚本;a2 甚至指向未微调的 base。**续期会拉起错误的模型、绑错误的端口**,而 runner 仍在问原端口 —— 落地就是第 4 例那种"静默灌 0" |

**它们的共同结构**:一条信息在传递链上被丢弃,而**丢弃点没有断言**。
下游拿到一个合法但错误的值(空字符串、None、0、默认值、截断的列表),
继续正常工作。

**四条防线**,按成本从低到高:

1. **兜底值必须能被识别为兜底。** 读不到就抛,或者回退到一个显然荒谬的哨兵
   值(-1),**绝不回退到一个看起来合理的魔数**(案例 5 的 `50`)。
2. **数量守恒要显式断言。** 进多少条、出多少条,不等就硬失败 ——
   `ship_dataset.sh` 的双端计数、`verify` 的图片存在性都是这个形状。
   案例 1 就是因为 build 那一层没有这条。
3. **参数的"生效值"必须打印,不能只打印"请求值"。**
   `image_max=20` 是请求,`稳态可见 15.7` 是生效 —— 案例 3 两者差了 21%。
   `build.py` 现在会打印 `image window: image_max=N fold_size=M`,是这条的落地。
4. **验证证据要完整读或按关键词 grep,禁止 `head` 当全貌**(案例 6)。
   同理:核对部署不能只看一个 grep 是否命中,要确认 pattern 本身能匹配 ——
   `grep -c 'of \${a.panel_n}'` 在单引号里 `\$` 是字面反斜杠,永远不匹配,
   曾让一次成功的部署被误判为失败,并据此做出两轮错误诊断。

**判据**:任何一处"取不到就用默认值"的代码,先问一句 ——
**如果这里悄悄用了默认值,下游会报错吗?** 答案是"不会"的,就是下一个案例。


### 9.1 第 7、8 例的修法:把断言放在丢弃点上(2026-08-22,commit `6b8d7778`)

这两例暴露的是同一件事:**ship 和 launch 之间没有任何东西检查"我要的东西
到了没有""我算的步数还成立吗"**。修法不是更小心,是把检查变成流水线的一环
(与 memory 里"质量检查随流水线走"同一条)。

**`ship_dataset.sh`** —— 建出 `val_swift.jsonl` 就带上,并核对远端行数、抽一张
val 的图确认路径可解析;**没有 val 时大声说出来**,因为 `--val-ratio 0.05` 已是
默认,缺失才是意外。val 不需要单独运图:build 把所有录取任务的截图写进同一个
`images/`,v11100 的 1358 张图对 1321 条 train 就是这部分盈余,不是泄漏。

**`preflight.py`** —— 收编了原先散在各 sbatch 里的图片解析检查,并加上没人做过
的那条:`save_steps` 必须整除每 epoch 步数。步数算法按 ms-swift/HF 的**实际**做法,
不是想当然的公式:

```
per_rank = N // ranks          # 余数直接丢掉,不摊给其他 rank
steps_per_epoch = ceil(per_rank / accum)   # 不满一组的尾巴也算一步
```

先 floor 再 ceil 这个**顺序**才是关键。6474 / 8 rank / accum 8 → 809 → **102**,
三个 epoch 306,与 job 252373 日志一致;换任何别的取整顺序会得到 101 或 102 全靠运气。

它还能 `--check-sbatch` 反向解析已经跑过的 sbatch,于是历史存档可以被审计,
而不是只管住未来的臂。**这个 checker 自己先被真值校验过**:它最初那条非贪婪的
`--dataset` 正则只吃到两个数据集里的一个,给 a5v 报了 105 步 —— 而日志白纸黑字
写着 485。检查器也要被检查。


### 9.2 第 9 例的判据:复制出来的配置,要查有没有指回源模板(2026-08-22)

**签名是"新东西默默替旧东西干活"。** 从模板复制一份新配置时,改动的是"这份配置
描述什么"(模型路径、端口、名字),**容易漏掉的是"这份配置引用谁"** —— 而后者
在正常路径上根本不执行,只在某个边界条件(撞墙、重试、回滚)才生效。

实例:五个 a 系列 serve 脚本从 nocap/base 模板复制而来,六个字段(作业名 / 模型 /
served 名 / 端口 / 墙 / 排除节点)都逐项核过,**唯独 `$SELF` 没人核** —— 因为它
不在"这份配置描述什么"的清单里,它在"这份配置引用谁"的清单里,而那份清单不存在。
全库扫完共 **7 处**指错。

三个条件同时成立才会引爆,而它们当时全部成立:

```
#SBATCH --signal=B:USR1@600     撞墙前 10 分钟触发 trap
28 份历史日志有 successor 记录   机制天天在跑,不是死代码
100 题面板 4.4h > 4h 墙          每个 a 系列臂都会撞
```

**没爆纯属侥幸**:此前所有可能撞墙的 serve 都被手动 `scancel` 了(base9b 的
252336 跑到 3:25:05 被停,教师两次 2:09 / 1:55),**从没有一个真的走到 4 小时**。
历史数据经逐个取证确认干净。

**判据**:
1. **复制模板产生的每一份新配置,先列出它"引用谁"** —— 自引用、兄弟脚本、
   下一环、回退目标 —— 再逐条核。描述性字段错了通常会立刻炸;引用性字段错了
   会安静地等在边界条件上。
2. **能自引用就别写死**。根治写法是让脚本问运行时自己是谁:
   `SELF=$(scontrol show job "$SLURM_JOB_ID" | sed -n "s/.*Command=\([^ ]*\).*/\1/p")`,
   **复制时不可能忘记改**。解析失败要置空 + FATAL —— **宁可没有后继,不要错误的后继**。
3. 日志里写死的地址(端口、路径)要和真实参数对齐。写错不致命,但**出问题时
   照着日志排错会查错地方**,把一次十分钟的定位变成一小时。

**与前八例的共同点**:错误不在数据里,在**管道里**;配置层写错了而运行层照跑。
第 4 例(serve 断档)、第 5 例(读取失败回退默认值)和本例是同一族的三幕。
