## 2 唯一成立的操作覆盖缺口:呈现/格式

八类操作在语料与 eval-50 的分布(关键词普查,口径粗但可复现):

| 操作类型 | 语料 v11-500 | eval-50 | 差 |
|---|---|---|---|
| 文件/目录搬运 | 10.1% | 6.0% | +4.1 |
| 计算/公式 | 15.2% | 14.0% | +1.2 |
| 内容编辑/修正 | 11.7% | 4.0% | +7.7 |
| 应用配置 | 16.4% | 16.0% | +0.4 |
| 导出/转换 | 7.4% | 8.0% | −0.6 |
| 查找/信息 | 7.2% | 6.0% | +1.2 |
| **呈现/格式** | **2.2%** | **20.0%** | **−17.8** |
| 新建产物 | 10.5% | 14.0% | −3.5 |

每条指令平均命中类数:语料 0.81 vs eval-50 0.88 —— **复合度相当,不是"语料太简单"**。

**解开率的对照(14 次跑并集):**

```
呈现/格式类   3/10 = 30%
其余所有类型  32/40 = 80%
```

细分:解开的 3 道全是**单对象单属性**;挂掉的全是**多对象同属性**或复合流程。

具体操作在 446 个训练任务里的出现次数:

```
文本对齐 align       0 / 446
字体/加粗 font       0 / 446
背景透明 transparent 0 / 446
颜色 color           2 / 446
新建工作表 Sheet2     1 / 446
图表 chart           3 / 446
```

### 2.1 根因在生成 prompt,不在生成器

`ostg/taskgen/prompts/single_json.txt` 只定义三种 grade:

| grade | 判据 | 能判格式吗 |
|---|---|---|
| probe (83%) | VM 内 python3,**无 openpyxl / python-docx / python-pptx** | ❌ |
| table (14%) | 宿主 openpyxl,规则只有 `check_cell → props.value`,方法 eq/ne/gt/ge/lt/le/approx/re | ❌ 全是值比较 |
| browser (3%) | 最终 URL 正则 | ❌ |

而 `<role>` 首段:「a task is worth writing only when a program can decide whether
it was done」,[USER] 结尾再强化一次。**判据表达不了格式属性 → prompt 命令丢弃 →
生成器系统性回避。** Qwen v11q2 同样 align 0.4% / font 1.3%,**换生成器无效**。

两条加重因素:
- rule 6:「prefer a different starting artifact when possible」明确劝阻预置 odp,
  而 eval-50 三道未解开的 impress 题**全部需要预置 deck**。
- rule 8:指令长度 d4-d5 硬闸 ≤300 字符(实测语料最长 299),而 eval-50 最长 506,
  未解开的 14 道均值 229、28.6% 超 250。

### 2.2 可能的改法(未实施)

架构本身支持委托给 OSWorld 自带 checker(`grade=table` 就是),只是当初只接了两种。

1. 加 `grade=pptx` / `grade=image`,照 table 的模式接 `compare_pptx_files`、
   `check_image_stretch_and_center`
2. rule 6 反向,给出 `--convert-to odp:impress8` 的可用配方
3. `intent` 轴五个值全是内容动作,需加一个 `restyle`/`format`
4. 刻意做成"同一属性、多个对象"—— 单对象的模型已经会了

⚠ 这些只保证"能生成这类题",不保证学生学得会。因果链后半段仍是假设。

## 3 失败的主形态:完成判断失败

634 条轨迹(230 通过 / 404 未通过):

| | 通过 | 未通过 | 倍数 |
|---|---|---|---|
| 平均步数 | 16.3 | 34.4 | 2.1× |
| 撞 50 步上限 | 5.7% | 47.0% | 8.2× |
| 动作重复率 | 18.1% | 36.0% | 2.0× |
| **连续重复动作率** | **4.5%** | **4.4%** | **1.0×** |
| 以 DONE 结束 | 85.7% | 42.3% | |
| 以 FAIL 结束 | 7.8% | 10.4% | |

**连续重复率完全相同是最关键的一行。** 模型不是 A→A→A 的退化生成,而是
A→B→C→A→B→C 的**周期性重做整套流程**。这是判断失败,不是生成失败。

失败的三种结局:

```
撞上限没做完        ~47%   它认为还没成功，一直重试到步数耗尽
以 DONE 结束但 0 分  ~42%   它认为已经成功了，其实没有
主动 FAIL           ~10%
```

**前两类 89% 是同一个病的两面:无法判断目标状态是否达成。**

### 3.1 撞上限的解剖

```
撞过上限的题共 40 道
  ├─ 26 道被别的跑解开过 —— 成功时最少步数中位 【10 步】
  └─ 14 道从没成功过
```

**同一道题顺利时 10 步,不顺时烧光 50 步。5 倍差距 → "题太长"不成立。**

排除"迷路":点击坐标离散度从通过组 83.9% 掉到撞上限组 **59.1%**(反复点同一批
位置,不是在探索)。

190 条撞上限轨迹的主导机制:

| 机制 | 占比 | 特征 |
|---|---|---|
| 打字主导 | 42.6% | press+typewrite ≥50% 的动作,逐行敲脚本 |
| 周期重做 | 36.8% | 重复率 ≥40%,反复重跑同一套 GUI 流程 |
| 其他 | 20.5% | |

## 4 多 action 单步:口径与训练的双重问题

### 4.1 实测比例

**推理侧:**

| 跑 | 总 step | 多 action 步 | 占比 | 单步最大 | 含多 action 的题 |
|---|---|---|---|---|---|
| eval50-r5lora | 1433 | 270 | 18.8% | 68 | 28/50 |
| eval50-b1epkeep | 1478 | 193 | 13.1% | 40 | 25/50 |
| eval50-kD | 1328 | 114 | 8.6% | **109** | 20/50 |

**训练侧(r5 语料,按 `<function=` 计数):**

| 语料 | 样本 | 多 tool_call | 占比 | 单样本最大 | 分布 |
|---|---|---|---|---|---|
| v11-500 | 5047 | 426 | **8.44%** | **29** | 1:4621 / 2:248 / 3:80 / 4:38 / 5+:60 |
| v11-100 | 1338 | 57 | 4.26% | 10 | 1:1281 / 2:27 / 3:15 / 4:11 / 5+:4 |

**训练数据本身就带这个习惯,学生是忠实复制的。**

### 4.2 harness 的真实行为(2026-08-18 实测,推翻了直觉)

`eval50-kD` 的 `5bc63fb9` step=21,109 条记录:

```
不同 screenshot_file 数:  109
不同 action_timestamp 数: 109
时间戳 14:03:52 → 14:09:46      一个 step 耗时 5 分 54 秒
相邻间隔 ≈ 3.2 秒                = sleep_after_execution 3
```

**每条 pyautogui 命令都单独执行、单独 sleep 3 秒、单独截图。**
模型只是拿不到这 109 张中间截图,只收到最后一张。

推论:
1. **batch 多个 action 不省任何 wall time**,只省模型调用次数
2. 代价是**全程盲操作**(此例 6 分钟)
3. 中间观测**都在盘上**,1:1 改造在观测层面可行 —— 但一个 batch 只有一段
   `<think>`,**推理过程不可分解**,重建的 1:1 样本只能共享或丢弃 rationale

### 4.3 口径问题

`max_steps=50` 不是交互次数的上界。同样"50 步",实际交互可以是 50 次到 1000+ 次
(kD 单步最大 109)。**跨臂比较建立在一个未定义的轴上。**

## 5 孤儿:harness 缺一个异常分支

历史上共 8 道题、11 次孤儿事件,分布在 4 次跑(其余 10 次零孤儿)。

```
eval50-gb128ep2keep  1     eval50-gb64keep  3
eval50-leanstock     2     eval50-kD        5(最多，且用 Klone L40S 服务)
```

**孤儿不是任务属性:** 最常孤儿的 `5bc63fb9` 被起 14 次只孤儿 3 次(21%)。
孤儿题平均 34.2 步 vs 非孤儿题 26.6 步(1.3×),但反例 `53ad5833` 平均 8.4 步、
从不撞顶,也孤儿过一次 → **时长是暴露系数,不是原因**。

### 5.1 死亡序列(两个孤儿完全相同)

```
Failed to get screenshot. Status code: 500
('Connection aborted.', RemoteDisconnected('Remote end closed connection'))
('Connection aborted.', ConnectionResetError(104, ...))
Failed to get screenshot.
Exception in EnvProcess-N: a bytes-like object is required     ← 关键
Traceback (most recent call last):
Failed to stop recording. Status code: 400  ×4
→ 不写 result.txt
```

末步命令数:`5bc63fb9` 93 条、`5d901039` 15 条崩;`09a37c51` 1 条则是**挂起
无报错**(另一种死法,疑与 Klone 隧道断连有关,日志有
`call_llm failed attempt 3/5: Connection error`)。

docker 事件全是 `kill` → `die`,**无 `oom` 事件**。WSL 内存 21G total / 6G
available,紧但没爆;第 4 个容器 `fmtw1-smoke` 是被 kill 的第一个。

### 5.2 因果链

```
题难 → 模型选「写脚本一次搞定」→ 单步塞进几十上百条命令
     → VM 内 HTTP 服务被请求风暴打崩
       → harness 未处理「截图拿不到」，抛 TypeError
         → EnvProcess 死，不写 result.txt → 孤儿
```

**VM 崩是基础设施抖动(难免);丢题是代码缺一个 except(可修)。**
若截图彻底失败时判 0 并写下 result.txt,孤儿归零,跑能自己走完。

### 5.3 重跑语义

`run_multienv_qwen.py` 全文无 retry/timeout。`get_unfinished()` 的行为:

- 有 `result.txt` → 计为已完成
- **无 `result.txt` → 把该题目录内容全部删除**,下次重跑

所以孤儿会在下次用同一 `--result_dir` 启动时自动重做,**但部分轨迹会被清空**
(要留证据得先拷走)。

⚠ `get_result()` 打印的 `Current Success Rate` 分母是**已出 result.txt 的题数**,
不是 50。缺题在那个打印里不计 0,直接不计 —— 与 `RESULTS.md` 的 `/50` 口径不同,
**别拿日志里那个数当分数**。
