```
图表 chart           3 / 446
```

### 2.1 根因在生成 prompt,不在生成器

`ostg/taskgen/prompts/single_json.txt` 只定义三种 grade:

| grade | 判据 | 能判格式吗 |
|---|---|---|
| probe (83%) | VM 内 python3,**无 openpyxl / python-docx / python-pptx** | ❌ |
| table (14%) | 宿主 openpyxl,规则只有 `check_cell → props.value`,方法 eq/ne/gt/ge/lt/le/approx/re | ❌ 全是值比较 |
| browser (3%) | 最终 URL 正则 | ❌ |

而 `<role>` 首段:「a task is worth writing only when a program can decide whether
it was done」,[USER] 结尾再强化一次。**判据表达不了格式属性 → prompt 命令丢弃 →
生成器系统性回避。** Qwen v11q2 同样 align 0.4% / font 1.3%,**换生成器无效**。

两条加重因素:
- rule 6:「prefer a different starting artifact when possible」明确劝阻预置 odp,
  而 eval-50 三道未解开的 impress 题**全部需要预置 deck**。
- rule 8:指令长度 d4-d5 硬闸 ≤300 字符(实测语料最长 299),而 eval-50 最长 506,
  未解开的 14 道均值 229、28.6% 超 250。

### 2.2 可能的改法(未实施)

架构本身支持委托给 OSWorld 自带 checker(`grade=table` 就是),只是当初只接了两种。

1. 加 `grade=pptx` / `grade=image`,照 table 的模式接 `compare_pptx_files`、
   `check_image_stretch_and_center`
2. rule 6 反向,给出 `--convert-to odp:impress8` 的可用配方
3. `intent` 轴五个值全是内容动作,需加一个 `restyle`/`format`
4. 刻意做成"同一属性、多个对象"—— 单对象的模型已经会了

⚠ 这些只保证"能生成这类题",不保证学生学得会。因果链后半段仍是假设。

## 3 失败的主形态:完成判断失败

634 条轨迹(230 通过 / 404 未通过):

| | 通过 | 未通过 | 倍数 |
|---|---|---|---|
| 平均步数 | 16.3 | 34.4 | 2.1× |
| 撞 50 步上限 | 5.7% | 47.0% | 8.2× |
| 动作重复率 | 18.1% | 36.0% | 2.0× |
| **连续重复动作率** | **4.5%** | **4.4%** | **1.0×** |
| 以 DONE 结束 | 85.7% | 42.3% | |
| 以 FAIL 结束 | 7.8% | 10.4% | |

**连续重复率完全相同是最关键的一行。** 模型不是 A→A→A 的退化生成,而是
A→B→C→A→B→C 的**周期性重做整套流程**。这是判断失败,不是生成失败。

失败的三种结局:

```
撞上限没做完        ~47%   它认为还没成功，一直重试到步数耗尽
以 DONE 结束但 0 分  ~42%   它认为已经成功了，其实没有
主动 FAIL           ~10%
```

**前两类 89% 是同一个病的两面:无法判断目标状态是否达成。**

### 3.1 撞上限的解剖

```
撞过上限的题共 40 道
  ├─ 26 道被别的跑解开过 —— 成功时最少步数中位 【10 步】
  └─ 14 道从没成功过
```

**同一道题顺利时 10 步,不顺时烧光 50 步。5 倍差距 → "题太长"不成立。**

排除"迷路":点击坐标离散度从通过组 83.9% 掉到撞上限组 **59.1%**(反复点同一批
位置,不是在探索)。

190 条撞上限轨迹的主导机制:

| 机制 | 占比 | 特征 |
|---|---|---|
| 打字主导 | 42.6% | press+typewrite ≥50% 的动作,逐行敲脚本 |
| 周期重做 | 36.8% | 重复率 ≥40%,反复重跑同一套 GUI 流程 |
| 其他 | 20.5% | |

### 4.2 harness 的真实行为(2026-08-18 实测,推翻了直觉)

`eval50-kD` 的 `5bc63fb9` step=21,109 条记录:

```
不同 screenshot_file 数:  109
不同 action_timestamp 数: 109
时间戳 14:03:52 → 14:09:46      一个 step 耗时 5 分 54 秒
相邻间隔 ≈ 3.2 秒                = sleep_after_execution 3
```

**每条 pyautogui 命令都单独执行、单独 sleep 3 秒、单独截图。**
模型只是拿不到这 109 张中间截图,只收到最后一张。

推论:
1. **batch 多个 action 不省任何 wall time**,只省模型调用次数
2. 代价是**全程盲操作**(此例 6 分钟)
3. 中间观测**都在盘上**,1:1 改造在观测层面可行 —— 但一个 batch 只有一段
   `<think>`,**推理过程不可分解**,重建的 1:1 样本只能共享或丢弃 rationale

### 4.3 口径问题

`max_steps=50` 不是交互次数的上界。同样"50 步",实际交互可以是 50 次到 1000+ 次
(kD 单步最大 109)。**跨臂比较建立在一个未定义的轴上。**

## 5 孤儿:harness 缺一个异常分支

历史上共 8 道题、11 次孤儿事件,分布在 4 次跑(其余 10 次零孤儿)。

```
eval50-gb128ep2keep  1     eval50-gb64keep  3
eval50-leanstock     2     eval50-kD        5(最多，且用 Klone L40S 服务)
```

**孤儿不是任务属性:** 最常孤儿的 `5bc63fb9` 被起 14 次只孤儿 3 次(21%)。
孤儿题平均 34.2 步 vs 非孤儿题 26.6 步(1.3×),但反例 `53ad5833` 平均 8.4 步、
从不撞顶,也孤儿过一次 → **时长是暴露系数,不是原因**。

### 5.1 死亡序列(两个孤儿完全相同)

```
Failed to get screenshot. Status code: 500
('Connection aborted.', RemoteDisconnected('Remote end closed connection'))
('Connection aborted.', ConnectionResetError(104, ...))
Failed to get screenshot.
Exception in EnvProcess-N: a bytes-like object is required     ← 关键
Traceback (most recent call last):
Failed to stop recording. Status code: 400  ×4
→ 不写 result.txt
```

末步命令数:`5bc63fb9` 93 条、`5d901039` 15 条崩;`09a37c51` 1 条则是**挂起
无报错**(另一种死法,疑与 Klone 隧道断连有关,日志有
`call_llm failed attempt 3/5: Connection error`)。

docker 事件全是 `kill` → `die`,**无 `oom` 事件**。WSL 内存 21G total / 6G
available,紧但没爆;第 4 个容器 `fmtw1-smoke` 是被 kill 的第一个。

### 5.2 因果链

```
题难 → 模型选「写脚本一次搞定」→ 单步塞进几十上百条命令
     → VM 内 HTTP 服务被请求风暴打崩
       → harness 未处理「截图拿不到」，抛 TypeError
         → EnvProcess 死，不写 result.txt → 孤儿
```

**VM 崩是基础设施抖动(难免);丢题是代码缺一个 except(可修)。**
若截图彻底失败时判 0 并写下 result.txt,孤儿归零,跑能自己走完。

### 5.3 重跑语义

`run_multienv_qwen.py` 全文无 retry/timeout。`get_unfinished()` 的行为:

- 有 `result.txt` → 计为已完成
- **无 `result.txt` → 把该题目录内容全部删除**,下次重跑

所以孤儿会在下次用同一 `--result_dir` 启动时自动重做,**但部分轨迹会被清空**
(要留证据得先拷走)。

⚠ `get_result()` 打印的 `Current Success Rate` 分母是**已出 result.txt 的题数**,
不是 50。缺题在那个打印里不计 0,直接不计 —— 与 `RESULTS.md` 的 `/50` 口径不同,
**别拿日志里那个数当分数**。

### 6.1 screenshot 在执行层就是 wait —— 一个语义化的空转别名

| 层 | 事实 |
|---|---|
| 声明 | `prompts.py:39` 把 `screenshot` 列为独立动作("Capture a new screenshot"),`:56` 还**鼓励**"take successive screenshots to see the results" |
| 执行 | `actions.py:331` `screenshot → WAIT`,与 `wait`(`:154/:325`)**同一条代码路径** |
| WAIT 语义 | `desktop_env.py:429-430` `time.sleep(pause)` —— 纯睡觉 |
| 冗余性 | 本 harness **每一步之后本来就返回新截图**,"拍一张看看"不提供任何额外信息 |

这是**上游官方动作空间**(纯净 worktree 同样 8 处声明),照搬自 computer-use 惯例
(那些环境里 screenshot 是真动作);在这里它是 wait 的别名。对模型的语义差别只在
意图:`wait` = 等加载,`screenshot` = 想再看看 —— 执行后果完全相同:烧一步、
睡 3 秒、得到一张反正都会给的截图。

**传授链**:提示鼓励 → 教师照做(语料 2.8%)→ **基座无视这条建议(0.0%)** →
SFT 把教师的服从蒸馏给学生并放大(2.0–6.0%)。"再看一眼"的习惯不是模型固有,
是提示种进教师、语料带给学生的。

### 6.2 四个读数

1. **screenshot:基座 0% → 臂最高 6.0%,教了且放大**。同一条传授机制也教会了

   语料里有什么就传什么。

3. **多 action 是三层叠加**:基座天然 5.0%,语料 7.6–8.3%,全量臂贴语料

## 7 命令风暴 → 客机崩溃:孤儿题的主通道找到了(2026-08-18 深夜)

执行层有两种放大(发现属"Tillicum 维护详情"会话,本节数字为独立复核):

| | 机制 | 占步比 | 单次放大 | 累计多付的命令 |
|---|---|---|---|---|
| 情况一 | 模型一次吐多个 tool_call,harness 逐个执行 | 7.5–17% | 2–5× | 3,759 条 |
| **情况二** | **单个多行 `type` 被 parser 拆成逐行 typewrite+enter**(`actions.py:292-303`,上游行为,仅 QwenAgent 分支拆) | 1.2–1.7% | **40–217×** | **5,319 条** |

情况二的种子在语料里:**202/6,385 个目标含多行 type**(教师 heredoc 一把梭的
习惯)。注意这些目标每个只有 1 个 tool_call —— **1:1 口径下完全合规,病在执行
层的放大,不在模型输出**。

### 风暴与崩溃的列联(全部 eval50 跑,轨迹级)

| | 崩溃 | 未崩 | 崩溃率 |
|---|---|---|---|
| 含风暴步(单 call ≥10 条命令) | 6 | 60 | **9.1%** |
| 无风暴步 | 2 | 632 | **0.3%** |

6/6 的崩溃发生在风暴**当步或之后**;两例(`81c425f5` step50 84 条、
`5bc63fb9` step41 **217 条**)崩在风暴步内部 —— 0 字节截图正是风暴执行到一半
时客机截图服务死亡的那一张。机制:一个 call 拆出上百条命令 → 每条一次
execute+screenshot HTTP → 客机 Flask 不堪连打 → connection reset →
`a bytes-like object is required` → 孤儿题。**§前文"客机截图服务为何死"的
开放问题,触发器即此。**

> n=8 次崩溃,样本小;但 30 倍率差 + 6/6 时序 + 2 例当步死亡,因果链硬。
> 另有 2 次无风暴崩溃 —— 它不是唯一通道,是主通道。

### 修法与分工

- **修法 B(执行层:多行 type 一条 typewrite 直发,不拆行)**:模型输出零改动、
  语料零清理、请求风暴消失。属上游行为修改 → 入 OPS.md 披露清单;12 个历史臂
  在拆行语义下跑,口径注记必须带。由"Tillicum 维护详情"会话实施中。
- **情况一(多 tool_call 批)**:行为层,总浪费更小、无崩溃关联;由 1:1 新采集
  (fmt-w1 起)与可选的语料拆分实验处理,优先级靠后。

### 修法 B 验收(2026-08-18,落地前;`tools/typefix_gate.py`)

方案(最小 robust,无 hardcode):`parse_internal_response` 的 `type` 分支在
`OSTG_TYPE_NO_SPLIT=1` 时不再逐行拆分,整段文本走**一条**
`pyautogui.typewrite()`;默认(变量不设)保持上游拆行,行为逐字节不变,仅
多一行 warning 留痕。启用与否由驱动脚本每次运行显式决定。

正确性前提全部实证,非推断:

| 前提 | 证据 |
|---|---|
| `\n` 在客机上就是回车键 | 客机 `desktop_env/server/requirements.txt` 钉死 PyAutoGUI==0.9.54;该版本 `_pyautogui_x11.py:282` 映射 `'\n': Return` |
| 单条 typewrite 与拆行键序相同 | 同文件基座分支 `parse_base_response` 从来就是一条 typewrite 不拆行,同一客机跑了所有基座 eval |
| 回放参数 = 生产参数 | 调用点 `main.py:298`;`--coord` 默认 `relative`,kD 命令行未覆盖 |

## 8 think 长度:语料收敛,学生发散 —— 失控是训练动力学产物,不是数据缺陷(2026-08-18 深夜)

**口径**:推理侧从 `traj.jsonl` 的 `response` 提取首个 `<think>…</think>` 的**内容**
长度(字符),按 `step_num` 去重(traj 每条执行命令重复记一行 response,不去重会把
多命令步平方);语料侧取 `messages` 里**最后一个** assistant —— `loss_scale last_round`
下它是唯一有梯度的那轮。早前一版误把历史轮 assistant 一起统计(r5 得到 n=76,919
而样本只有 6,385),那是 context 的分布,不是训练目标的。

  (没学到收敛)。**两头不靠**:丢了 base 的稳定,也没拿到教师的按需分配。

### 8.2 但语料的训练目标是收敛的 —— 而且 cap-2048 硬生效

### 8.3 结论:这条线在数据侧已经做到头了

```
r5 训练目标   最大  7,104 字符
      ↓
r5lora 产出   最大 46,519   (6.5×)
kD    产出    最大 360,072  (51×)
```

**学生产出了训练数据里根本不存在的行为,放大 50 倍。** 中位也从 241 涨到 461–783。

由此:

1. **失控不是从教师学的**(教师中位 268、最大 28,495),**也不是 4B 固有的**
   (base 最大 3,392)。它是 SFT 过程自己长出来的。
2. **cap-2048 那 +4.0 分留在噪声里是有机制解释的** —— 它修的是数据尾巴,而病灶
   在动力学。数据侧已经 0 条超标,继续在 think 长度上做数据清洗**没有剩余空间**。
3. 要修学生的思考失控,只能从训练侧(长度正则 / 目标加权)或推理侧(think 预算、
   长度惩罚)入手。这是一个**未立项**的方向,此前所有努力都花在数据侧。
4. 与 §3「完成判断失败占 89%」和 `SFT_DATA.md`「>2k think 的步弱步率 41%,
   1k–2k 带 0%」拼合:长 think 与"想完不做"同现,而长 think 本身是 SFT 引入的。

**未验证**:上述是分布层面的观察,尚未做因果实验(例如同语料下加长度正则再训一臂)。
"训练动力学导致发散"是目前最省事的解释,不是被证明的机制。

### 8.4 膨胀是"困境响应",不是普遍冗长;cap 只在数据侧生效

按 step 分组看 think 中位长度(字符),立刻能看出形状:

| 臂 | 1–5 | 6–10 | 11–20 | 21–30 | 31–40 | 41–50 | 膨胀 |
|---|---|---|---|---|---|---|---|
| **base 未微调** | 1296 | 1465 | 1474 | 1484 | 1547 | 1547 | **1.19×** |
| **教师 27B** | 222 | 209 | 314 | 366 | 320 | 383 | 1.73× |
| gb64keep(B,无 cap) | 284 | 261 | 378 | 777 | 864 | 777 | 2.74× |
| bskeep(Bs,有 cap) | 314 | 380 | 439 | 1085 | 1072 | 1155 | 3.68× |
| r5lora | 253 | 225 | 683 | 1198 | 1305 | 2031 | 8.0× |
| kD r5 全量 | 258 | 344 | 451 | 401 | 992 | **2909** | **11.3×** |

但"越到后面想得越长"有一个混淆:**更强的臂能撑到更后面,而后段本来就是难题**。
按题目结局分组、只取跑够 20 步的题,把幸存者效应排掉:

| 臂 | 成功题 前5→末5 | | 失败题 前5→末5 | |
|---|---|---|---|---|
| **base 未微调** | 1474 → 1484 | **1.01×** | 1362 → 1492 | **1.10×** |
| gb64keep(B,无 cap) | 355 → 436 | 1.23× | 267 → 738 | **2.76×** |
| bskeep(Bs,有 cap) | 342 → 383 | 1.12× | 385 → 1259 | **3.27×** |
| kD(r5 全量) | 355 → 1060 | 2.99× | 341 → 1839 | **5.39×** |

**base 在两种结局下都是平的(1.01× / 1.10×)——它做不出来时不会多想一个字。**
SFT 臂在成功题上基本不膨胀(1.12–1.23×),在失败题上剧烈膨胀(2.76–3.27×,
kD 5.39×)。所以 SFT 装上的不是"啰嗦",而是 base 没有的一个行为:
**卡住时越想越多**。这与 §3「完成判断失败占 89%」同源——判断不了成没成,
于是原地重做且每轮想得更长,直到烧光 50 步或打满 token。

**cap-2048 的完整效果(双侧)**:

| | 数据侧 | 推理侧(成功题) | 推理侧(失败题) | eval-50 分数 |
|---|---|---|---|---|
| cap-2048 | **硬生效**:训练目标最大 28,495→7,104,>8192 字符的目标 60→**0** | 1.23×→1.12×,略好 | 2.76×→**3.27×**,略差 | +4.0(0.76σ,噪声内) |

**cap 把数据尾巴剪干净了,却没有抑制推理时的困境膨胀。** 这是那 +4.0 停在噪声里
的机制解释,也再次指向 §8.3 的结论:病灶不在数据侧。

**一条不能简化掉的反例**:kD 膨胀最严重(成功题 2.99×、失败题 5.39×),却是全场
最高分 49.81%。所以"膨胀 = 差"**不成立** —— 更可能是 kD 更愿意在难题上继续尝试,
而尝试同时带来分数和膨胀。此处不下因果结论。

**未验证 / 下一步**:上述全是观察性证据,不能区分「难题→想得长且失败」(长度是难度
的指标)与「想得长→陷进去→失败」(长度是原因)。最便宜的因果实验在**推理侧、
无需重训**:同一 checkpoint 把 `--max_tokens` 从 81920 压到 8192(仍远高于训练目标
最大值 7,104 字符≈1,776 token,即压制不会把模型推出训练分布),跑一轮 eval 对照。
分数不降或上升 ⇒ think 长度是"氛围灯";分数显著下降 ⇒ 长思考确有功能。

### 8.5 "think 长 → 失败"是共因,不是因果:题内配对在强臂间不成立

先做题内配对(同一道题上,成功的臂 vs 失败的臂的 think 中位长度;题目难度因此
被控制掉),全部 14 臂给出一个看似很强的结果 —— 但按臂的强弱分层后它就塌了:

| 分层 | 臂数 | 可比题 | 成功更短 : 成功更长 | 中位相对差 |
|---|---|---|---|---|
| 全部臂 | 14 | 32 | **25 : 7**(≈3.2σ) | +41% |
| **仅强臂(eval-50 ≥40%)** | 8 | 18 | **11 : 7**(p≈0.48) | **+6%** |
| 仅弱臂(<40%) | 6 | 17 | 11 : 6 | +64% |

**在能力相当的臂之间效应消失。** 那个 25:7 是"强臂想得短且做得对 / 弱臂想得长
且做不对"两组之间的对比拉出来的 —— **模型能力是共因**,不是"长 think 导致失败"。

**结论**:think 长度是能力的**伴随症状,不是可拉的杠杆**。据此预期:强行压缩强臂的
think **不会**提升其 eval-50 分数。这同时降低了 §8.4 末尾那个干预实验的优先级——
它要回答的问题从"缩短能否提能力"(预期否)变成"缩短是否无害"(若无害则可省算力
与 wall time,think 短 = 步更快)。

**方法学注记**:这是一次典型的"用已有数据先杀假设"——零 GPU、几分钟,把一个
3.2σ 的观察削成不显著。任何跨臂的相关性结论都必须先做能力分层,否则强弱两组的
系统差会伪装成机制。

**做干预实验时的坑(若仍要做)**:不能简单压 `--max_tokens`。截断会落在 think 中间,
导致该步没有 `<tool_call>` 输出 → 被 harness 空解析兜底(§3、`parser.py:97`)→
人为制造失败,污染的正是要测的那个量。正确做法是 budget forcing:think 达预算时
强制注入 `</think>` 让模型收尾,需改客户端两阶段生成。另注:`reasoning_effort`
三档(xhigh/medium/low)是 **Qwen3.8 教师模板独有**,学生 Qwen3.5-4B 的基座模板与
SFT checkpoint 模板均 **0 处命中**,不能拿它当现成开关。
